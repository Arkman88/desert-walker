# Desert Walker — ТЗ для Codex: универсальные GameObject / GameObjectGroup

**Статус:** архитектурное ТЗ, не описание реализованного функционала.  
**Контекст:** браузерная 3D-игра desert-walker, React/TypeScript/Three.js (фактические библиотеки и структуру проекта проверить в репозитории).  
**Основание:** `CURRENT_MECHANICS.md` от 15.11.2026, схема сохранений 16; обсуждение универсальных групп объектов.  
**Главная цель:** обеспечить единый способ описания и размещения составных объектов (строения, лагеря, транспорт, механизмы и другие комплексы), сохраняя независимую логику их деталей.

## 0. Инструкция Codex: сначала аудит, затем минимальный вертикальный срез

1. Прочитай `CURRENT_MECHANICS.md`, `PROGRESS.md`, `DEVELOPMENT_PLAN.md`, если они существуют, и найди в коде текущие системы мира, procedural generation, интеракций, коллизий, крафта, размещения, хранилищ и сохранений.
2. Составь краткую карту фактических модулей и точек интеграции. **Не придумывай имена файлов, API и существующие компоненты** — опирайся на реальный код.
3. Определи минимальные изменения, необходимые для новой архитектуры. Не переписывай весь проект и не удаляй действующие механики.
4. Реализуй **только этап 1** (каркас архитектуры + одна хижина); этап 2 (насосная станция) — отдельным последующим шагом после проверки. Не добавляй новые механики ремонта, транспорта и свободного строительства без отдельного согласования.
5. Обратная совместимость старых сохранений (включая схему 16 и версии 1–15) **не требуется**: проект — прототип. Разрешается ввести новый формат без миграций. Обязательно реализуй надёжное сохранение/загрузку нового формата, стабильные ID и явное предупреждение при несовместимом сохранении. Никогда не удаляй старые данные молча.
6. После реализации отчитайся: что изменено, как проверить, какие ограничения остались, результаты тестов/сборки.

## 1. Основные понятия

### GameObject

**Логическая сущность**, а не обязательный отдельный `THREE.Mesh`. Имеет стабильный ID, ссылку на определение типа, локальный или мировой transform и набор данных компонентов. Примеры: стена, дверная створка, ящик, насос, колесо, костёр.

### GameObjectGroup

**Логическая композиция** объектов с уникальным ID, типом (`building`, `vehicle`, `machine`, `camp` и т. п.), корневым transform и составом. Группа определяет контекст сборки и принадлежность; не обязана совпадать с единственным GLB или render group.

### GameObjectDefinition / GroupDefinition

Статические данные/префабы: какие компоненты и визуальные ресурсы использовать, допустимые сокеты, типовые части и их начальные локальные трансформации. Экземпляр хранит только индивидуальное состояние и ссылки на определения.

### AssemblyRules

Отдельный реестр правил, выбираемый по `group.type`. Отвечает за допустимость добавления/удаления, размещение и совместимость соединений. Не должен содержать прямых вызовов React или Three.js. **Правила группы отличаются от компонентов поведения отдельного объекта.**

### Membership vs Connections

`members` — кто входит в группу; `connections` — какие детали связаны физически/функционально. Ящик внутри здания может быть членом группы без крепления; дверь соединена с дверным проёмом через шарнир; насос и труба соединены портами. Не выводить физические связи автоматически из членства.

## 2. Пример контракта (адаптировать к реальному коду)

```ts
type Id = string;
type Vec3 = readonly [number, number, number];
type Quat = readonly [number, number, number, number];

type Transform = { position: Vec3; rotation: Quat; scale: Vec3 };

type GameObjectInstance = {
  id: Id;
  definitionId: string;
  transform: Transform; // local для member группы, world для самостоятельного объекта
  components: Record<string, unknown>; // сериализуемое состояние, с типизированным реестром
};

type GroupConnection = {
  id: Id;
  fromObjectId: Id;
  toObjectId: Id;
  kind: 'snap' | 'fixed' | 'hinge' | 'port';
  fromSocket?: string;
  toSocket?: string;
};

type GameObjectGroupInstance = {
  id: Id;
  type: string;
  definitionId?: string;
  transform: Transform; // world
  members: GameObjectInstance[];
  connections: GroupConnection[];
  state: Record<string, unknown>;
};

type ValidationResult =
  | { ok: true }
  | { ok: false; code: string; message: string };

interface AssemblyRules {
  validateAdd(group: GameObjectGroupInstance, part: GameObjectInstance): ValidationResult;
  validateRemove(group: GameObjectGroupInstance, partId: Id): ValidationResult;
  validateConnection(group: GameObjectGroupInstance, link: GroupConnection): ValidationResult;
}
```

**Контракт иллюстративный:** не требуется копировать его дословно. Нужны типизированные данные компонентов (discriminated unions / registry), валидация входных данных сохранения и отсутствие циклических ссылок. Для самостоятельных объектов явно фиксировать систему координат; не использовать неявные преобразования между world/local.

## 3. Принципы реализации

- **Data ≠ render:** сериализуемые объекты не хранят `THREE.Object3D`, геометрию, материалы, React-элементы, функции или ссылки на DOM.
- **Composition over inheritance:** поведение из компонентов (`Renderable`, `Collider`, `Interactable`, `Storage`, `Openable`, `Durability` — только необходимые сейчас). Не строить цепочку классов `Building > Hut > ...`.
- **Registry:** отдельные реестры определений объектов, типов групп, сборочных правил и фабрик визуализации.
- **Stable IDs:** идентификаторы экземпляров стабильны между генерацией, выгрузкой чанка и загрузкой сохранения. Для процедурных объектов — детерминированный ID из seed + координат/ключа объекта либо другой устойчивый механизм; для созданных игроком — уникальные сохраняемые ID. Не полагаться на индекс массива.
- **Transform:** world transform группы + local transform детали; корректное обновление при переносе/повороте группы. Уточнить оси/единицы модели (для имеющейся хижины Y вверх, вход по -Z).
- **Ownership:** одна логическая сущность не должна одновременно принадлежать двум группам. Перемещение между группами — явная операция; вложенные группы разрешать только если действительно нужны, с защитой от циклов (в первом этапе можно запретить).
- **Atomic operations:** добавление, удаление, взаимодействие и перенос предметов выполняются целиком или не выполняются; не допускаются дублирование лута и частичное списание материалов.
- **Visual assets:** GLB — ресурс рендера, не источник бизнес-правил. Имена узлов можно использовать для первоначального mapping, но хранить явную конфигурацию деталей и pivot/anchors.

## 4. Правила сборки по типу группы

| Group type | Примеры частей | Принцип правил (позднее) |
|---|---|---|
| `building` | стены, проёмы, дверь, крыша, навес | сокеты/сетка, опора, допустимые проёмы |
| `vehicle` | рама, колёса, двигатель, бак | фиксированные слоты, совместимость запчастей |
| `machine` | насос, двигатель, трубы, резервуар | механические крепления и порты подключения |
| `camp` | навес, ящик, кровать, костёр | область размещения, коллизии, доступность |

Эти правила **не требуется реализовать полностью в этапе 1**. Достаточно доказать, что правила выбираются по типу группы, а не зашиты в рендерер конкретной хижины. Поддерживать понятные причины отказа валидации.

## 5. Этап 1 — работающий вертикальный срез: одна хижина

**Вход:** существующая хижина `desert_hut_v4.glb` (если ресурс присутствует в проекте; иначе использовать существующий домик, не выдумывать отсутствующий путь). Текущий GLB может быть визуально монолитным — разрешается временный mapping узлов в логические части без немедленного изготовления новых моделей.

**Нужно сделать:**

1. Добавить базовые модели данных, реестры и минимальный API групп и объектов.
2. Описать prefab `desert_hut` типа `building`, включающий логические части: `wall_shell` (на первом этапе может быть единым статическим объектом), `roof`, `door`, `canopy`, `crate` (если ящик уже создан отдельно игровой системой — **не дублировать**).
3. Дверь и ящик должны сохранять действующие способы взаимодействия. Если существующая дверь не интерактивна, **не объявлять открывание уже реализованным**; предусмотреть интерфейс и описать как будущую работу.
4. Использовать текущую систему коллизий: проёмы не должны блокироваться общим box collider всего здания; невидимые препятствия не должны оставаться после удаления объекта.
5. Привязать prefab к существующей процедурной генерации **одного** типа хижины без изменения плотности локаций, seed-логики и уже сохранённых позиций.
6. Проверить выгрузку/повторную загрузку чанка, повторный вход в игру и восстановление состояния деталей.
7. Добавить простую отладочную визуализацию/логирование ID группы, её типа, списка членов и соединений (только dev mode).
8. Не включать UI строительства, перенос стен, ремонт крыши, разрушение дома или разборку машины в первом этапе.

**Результат:** на экране обычная хижина, но в игровом состоянии она является `GameObjectGroup`; ящик и прочие существующие взаимодействия работают как прежде. Правила групп можно тестировать без запуска WebGL.

## 6. Этап 2 — проверка универсальности на насосной станции (ПОСЛЕ согласования)

Создать `machine` prefab: корпус станции, насос, резервуар, соединительная труба, источник питания (визуальные заглушки допустимы). Дать объектам стабильные ID и связи `port`/`fixed`. Добавить **только проверку сборочной совместимости** (например, насос нельзя подключить к несовместимому порту), сохранение и повторную загрузку. Не реализовывать производство воды, электросети, новые рецепты или экономику ресурсов без отдельного ТЗ.

Цель — доказать, что те же `GameObject`/`GameObjectGroup`/registry работают с другим типом группы, а не создать вторую независимую систему для станций.

## 7. Интеграция с действующими механиками

Согласно `CURRENT_MECHANICS.md`:

- **E и взаимодействия:** ящики, костры, кровати, поднятые вещи; стандартная дальность взаимодействия до 3 м, препятствия могут перекрывать доступ. Сохранить.
- **Ящики:** перенос вещей, ограничения вместимости, чтение записок, разборка пустого ящика на 4 доски, отсутствие повторного появления после разборки. Сохранить, исключить дублирование контейнеров при загрузке GLB.
- **Крафт/размещение:** существующие рецепты, предпросмотр, подтверждение E, отмена Q, проверки уклона/коллизий, одноразовый расход комплекта. Не менять.
- **Лагерь:** навесы, костры и кровати уже размещаются и сохраняются; в первом этапе допустимо оставить их старым кодом через адаптер.
- **Генерация:** сохранить стабильность процедурных локаций, лута и истории его подбора/разборки.
- **Сохранения:** существующая схема 16 описывает прежний формат. Поддерживать чтение версий 1–16 не требуется. В новой игре должны корректно сохраняться и восстанавливаться карта, инвентарь, сооружения, лут, группы и состояние мира в **новом** формате.

**Не считать существующими:** свободное строительство стен, ремонт домов, восстановление насосной станции и универсальную разборку предметов — они перечислены как не реализованные. Архитектура должна их позволять, но это не часть этапа 1.

## 8. Сохранения нового формата (без миграций)

**Решение для прототипа:** обратная совместимость сохранений версий 1–16 не нужна. Не писать миграции 16→17, legacy-адаптеры или тесты загрузки старых fixtures только ради совместимости. Допускается новая версия схемы, номер выбрать по фактической реализации проекта.

1. Определить единый сериализуемый формат для новых `GameObject`, `GameObjectGroup`, компонентов и соединений; не сохранять ссылки на `THREE.Object3D` и React-объекты.
2. Хранить явный `saveVersion` и стабильные ID экземпляров. Обеспечить восстановление состояния после перезапуска, выгрузки/загрузки чанков и повторной загрузки.
3. При несовместимой версии или невалидных данных **не перезаписывать и не удалять старое сохранение автоматически**. Показать понятное предупреждение и предложить начать новую игру; очистка/замена — только после явного действия пользователя. По возможности предусмотреть экспорт/резервную копию до сброса.
4. В новой игре должны сохраняться и восстанавливаться существующие по смыслу механики: инвентарь, экипировка, потребности, карта, контейнеры и их содержимое, построенные объекты, лут и история подбора, состояния групп, время и погода.
5. Не дублировать ящики, лут и части групп после повторного входа или загрузки. Процедурные неизменённые объекты восстанавливать из seed/prefab, сохраняя только необходимые изменения.
6. При отсутствующем prefab/asset или повреждённых данных предусмотреть диагностику и безопасную обработку ошибки, а не молчаливую порчу сохранения.
7. Тестировать round-trip нового формата, повторную загрузку, стабильность ID и сценарий несовместимой версии. **Не требовать тестов миграции со схемы 16.**

## 9. Производительность и рендеринг

- Логические `GameObject` **не равны** draw calls. Статические детали могут использовать общий GLB, mesh batching или instancing.
- Не создавать отдельный React-компонент для каждого мелкого декоративного камня или балки.
- Разделять статические и динамические части: стены/крыша — статические, дверь/ящик — интерактивные при необходимости.
- Корректно освобождать ресурсы при выгрузке чанка; не уничтожать общие геометрии/текстуры, используемые другими экземплярами.
- Сохранить текущее качество текстур и материалы хижины, не подменять их старыми. Новая архитектура сама по себе не исправляет UV-швы.
- Сравнить FPS, draw calls, число мешей и потребление памяти до/после на одинаковой сцене и одинаковом устройстве. Не заявлять «60 FPS гарантировано» без замеров.

## 10. Тесты и критерии приёмки этапа 1

### Unit

- Создание группы с уникальными ID и типом.
- Корректное разрешение `GroupRules` по `group.type`.
- Запрет недопустимой детали/соединения с понятной причиной.
- Проверка ссылочной целостности соединений (неизвестные ID, дубликаты, удалённые участники).
- Корректное вычисление world transform из group + local transform.
- Сериализация/десериализация с сохранением IDs, типа и состояний.

### Integration

- Хижина появляется там же, где до рефакторинга, и имеет прежние коллизии.
- Игрок может пройти в предусмотренный дверной проём; нет невидимой сплошной коллизии.
- Ящик открывается через E; лут не дублируется после выгрузки/загрузки чанка.
- Пустой ящик разбирается по прежним правилам; после повторного входа не возрождается.
- Существующий крафт/размещение навеса, костра, кровати и ящика не сломан.
- Новое сохранение корректно загружается после перезапуска; состояние игрока, карта, инвентарь, группы и контейнеры восстанавливаются. Несовместимое старое сохранение вызывает предупреждение и не удаляется без подтверждения.
- Смена типа группы меняет применяемые правила в unit-тесте без правок рендерера.

### Definition of Done

- Есть рабочий типизированный core и минимум один prefab группы.
- Хижина использует core, а не отдельную специальную реализацию `HutGroup`.
- Проходят доступные тесты, typecheck и build (команды взять из проекта).
- Есть краткий документ для разработчика: как добавить новый `GameObjectDefinition`, `GroupDefinition` и `AssemblyRules`.
- Есть отчёт с реальными замерами/оговоркой, если профилирование не проводилось.
- Никаких незаявленных изменений баланса, управления, процедурной генерации и существующих механик.

## 11. Не входит в текущий объём

Свободное строительство, ремонт/разрушение, графический редактор групп, физическая симуляция всех соединений, управление транспортом, работающая гидравлика, электрические сети, переработка всех предметов, сетевой мультиплеер, масштабный рефакторинг мира. Всё это отдельные этапы после подтверждения базовой архитектуры.
