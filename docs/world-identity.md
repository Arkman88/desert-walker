# T01: идентичность legacy мира

Дата: 17.11.2026.

`src/features/terrain/worldIdentity.ts` задаёт поддерживаемый мир `{ seed: 'legacy', generatorVersion: 1 }`. `legacy` — имя существующего фиксированного набора hash/noise и размещения, а не новый вход PRNG. Константа 18.37 в hash и все остальные алгоритмы, координаты и ID сохранены. Произвольные seed и переключение генераторов пока не поддерживаются.

## Сохранения

Обёртка survival schema 19 получает дополнительное поле:

```json
{
  "version": 19,
  "worldIdentity": { "seed": "legacy", "generatorVersion": 1 },
  "state": "SurvivalState (с T02 включает progression; см. progression.md)"
}
```

`version` — версия структуры сохранения, `generatorVersion` — версия генерации и стабильных ID мира. Это независимые контракты. `serializeSurvivalSave` — единая запись обёртки для обычного сохранения и новой игры через SaveRecovery.

Стратегия совместимости:

- Schema 19 без поля worldIdentity трактуется как legacy. Парсинг и открытие игры сами не записывают данные. При следующем успешном изменении/flush метаданные добавляются к той же записи.
- Явное поле обязано совпадать с поддерживаемым миром. null, неверные типы, неизвестный seed или generatorVersion не превращаются автоматически в legacy.
- Повреждённый/несовместимый slot остаётся под существующим write-lock, доступен точный export. Явный выбор новой игры сохраняет резервную копию отвергнутого slot и позы; отказ backup не разрешает продолжение.
- Старые версии schema, которые до T01 не поддерживались, по-прежнему не принимаются. Новая миграция не обещает чтение schema 1–18.
- Ключи survival, player pose schema 1 и resources schema 1 раздельны. T01 не меняет pose/resource формат и не вводит общую транзакцию между ними.
- Существующие нормализации загрузки (обновление домов/ящиков/станции, очистка пользовательских маркеров) сохраняются. Это не новая логика T01.

Весь runtime пока поддерживает ровно один мир: guard загрузки проверяет метаданные до обработки групп; генераторы продолжают работать без новых аргументов и вычислений каждый кадр. Перед поддержкой второго мира потребуются выбор генератора и отдельное решение для pose/resource слотов.

## Baseline и регрессия

До изменений production-кода сняты фиксированные JSON fixtures:

- `tests/fixtures/legacy-world-v1.json`: height/hash на положительных, отрицательных и дальних координатах, оазисы, исходные POI, контейнеры и предметы, деревни, начальные/уличные группы, демонстрационные и региональные руины, скважина. Включены transforms и стабильные ID.
- `tests/fixtures/legacy-survival-v19.json`: валидный заполненный slot без worldIdentity с открытой технической дверью, историей лута, монтировкой, оставленным предметом, навесом, ящиком с частично заполненной флягой, кроватью и горящим костром.

`tests/legacy-world-snapshot.mjs` собирает контрольные значения, `tests/world-identity.mjs` сравнивает их с fixtures через exact deep equality в текущем JS runtime, проверяет реальный store, запись/reload, соседние слоты, write-lock, failed writes/retry, export/backup/reset. Fixtures не генерируются при npm test: изменение ожидаемых значений должно быть отдельным осознанным решением. Все координаты мира этими выборочными fixtures не покрываются; остальные domain-тесты дополняют baseline.

## Однократная очистка по запросу пользователя

После T01 пользователь явно выбрал автоматическую очистку старых saves при следующем запуске. Это уточнение меняет политику первого запуска: `main.tsx` вызывает `resetLegacySaves` до рендера App и чтения survival/позы. Если отметки `desert-walker.legacy-reset.v1=done` нет, удаляются три активных слота: survival, player pose, resources — независимо от их содержимого и наличия WorldIdentity. Поэтому первый запуск этой версии начинает чистую игру, включая случаи повреждённого старого slot.

Резервные копии и прочие ключи localStorage не удаляются. Отметка ставится только после успешного удаления всех трёх слотов. При отказе любого шага App не монтируется, показывается ошибка; при перезагрузке очистка повторяется. После отметки новые saves, в том числе впоследствии повреждённые, автоматически больше не удаляются: действует обычная загрузка и SaveRecovery. Совместимый parser T01 и его fixtures сохранены для проверки контракта, но не обходят согласованную очистку первого запуска.

`tests/legacy-save-reset.mjs` проверяет чистые initial state/pose/resources, сохранность посторонних ключей и backup, отсутствие повторного сброса после сохранения нового прогресса, повторную очистку после отказа каждого storage-шага. Работа выполняется только при запуске, не в игровом цикле. Это не генерация нового seed: тот же мир восстанавливается в исходном состоянии.

## Ручная проверка пользователем

1. Запустить обновлённую игру: ожидаются исходная позиция, стартовые припасы, отсутствие прежних построек и сброшенная история лута/двери.
2. Выполнить сохраняемое действие, например изменить состояние бури, и перезагрузить: новый прогресс должен сохраниться, повторной очистки быть не должно.
3. После первого запуска при необходимости проверить worldIdentity в survival-записи: version остаётся 19, seed — legacy, generatorVersion — 1.
4. Проверку SaveRecovery с неизвестной identity выполнять на тестовой копии **после** однократной очистки: новый повреждённый slot должен остаться под защитой.
