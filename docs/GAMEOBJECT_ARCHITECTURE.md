## Данные и правила

`features/gameObjects/gameObjectModel.ts` содержит только сериализуемые типы. `GameObject` имеет стабильный ID, definitionId, локальную трансформацию, компоненты и собственное состояние. `GameObjectGroup` имеет ID, type, definitionId, мировую трансформацию, members, connections и состояние. Метры, Y вверх, нормализованные кватернионы, положительный масштаб. Вложенных групп нет.

Реестр в `gameObjectRegistry.ts` хранит определения объектов, prefab групп и политики сборки. `gameObjectCatalog.ts` — точка регистрации активного содержимого приложения. Ядро не импортирует каталог, React или Three.js. Политика выбирается через `group.type`. Правила получают полное кандидатное состояние, включая добавляемую деталь. Общие проверки обеспечивают существование определений, совместимость/занятость сокетов, ссылочную целостность и уникальность ID. Политика здания проверяет состав prefab, компоненты, монтажную трансформацию и запрет удаления опоры с зависимыми деталями.

`gameObjectOperations.ts`: создание, валидация, добавление, удаление, замена, подключение/отключение и изменение компонентов. Результат операции содержит новую логическую версию группы либо понятный отказ; исходные данные не мутируют. Удаление детали удаляет её соединения. Замена сохраняет ID места. Ремонт можно выразить обновлением durability; игровой механики ремонта и её UI нет. Публикация через store происходит после успешной проверки, без пересоздания GLB и GPU-ресурсов.

`gameObjectValidation.ts` проверяет неизвестные данные на границе загрузки: компоненты, конечные числа, трансформации, состояния, массивы и связи. `gameObjectTransform.ts` вычисляет world point последовательным применением local и group transform; сочетание неравномерного масштаба и поворота не теряет shear при разложении.

## Хижина

Prefab `desert_hut`, type `building`, группа `hut:test:v1`:

| Часть | Компоненты/связи |
| --- | --- |
| wall_shell | Стены и рама двери; монтажные сокеты |
| roof | Крыша и брёвна; fixed к wall_shell |
| door | Створка, накладки и ручка; door.opened, interaction, hinge к wall_shell |
| window | Деревянная рама окна; fixed к wall_shell |
| canopy | Навес, балки и опоры; fixed к wall_shell |
| crate | Встроенный ящик; storage/interaction; член группы без крепления |
| props | Бочка, порог, обломки; член группы без крепления |

У деталей есть render, collider и durability. Наличие компонента не создаёт отдельный Mesh. Имена GLB перечислены в явном mapping `hutParts.ts`; они не определяют допустимость сборки. Компонент storage не содержит вторую копию лута: текущие вещи разрешаются прежней системой контейнеров и collectedIds/dismantledIds. Разобранный ящик остаётся историческим логическим членом, но его визуализация, контейнер и коллизия отключены через существующее состояние разборки.

`hutRenderAdapter.ts` один раз привязывает существующие узлы к частям. Смена состояния обновляет трансформации/видимость; ресурсы и материалы не клонируются. Дверь использует прежний hinge pivot. E переключает открытое/закрытое состояние, точки взаимодействия следуют за текущей створкой, закрывание поверх игрока запрещено. Снятие удаляет её соединение, скрывает створку и убирает коллизию. Дверь хранится в группе со своим ID, состоянием открывания и прочностью; отдельного предмета в инвентаре или падающей двери в мире нет. Повторная установка возвращает соединение. Установка поверх игрока отклоняется. Для первого этапа это отладочная проверка сборки.

Прокси коллизий используют существующие mesh-derived bounds и те же local/world transforms. Общего box всего дома нет, дверной проём остаётся открытым после снятия. Закрытая/открытая установленная дверь остаётся физическим препятствием в соответствующей позиции.

## Как добавить новое содержимое

1. В каталоге своей игровой системы описать `GameObjectDefinition`: ID, начальные компоненты, сокеты и совместимость.
2. Описать `GroupDefinition`: type, ключи частей, ссылки на определения и начальные local transforms. Для процедурного экземпляра передавать ID из устойчивого ключа генерации, а не индекса массива; для созданного игроком — уникальный сохраняемый ID.
3. Зарегистрировать определения и `AssemblyRules` для нового type. Новая политика задаёт добавление, удаление, соединения и размещение; базовые операции не меняются. Общие правила типа можно использовать для нескольких prefab.
4. Подключить регистрацию в `gameObjectCatalog.ts`. Написать адаптер ресурса рендера и адаптер к существующим коллизиям/взаимодействиям соответствующей системы. Подключить их в сборке сцены/препятствий и генерации. Ссылки на Three.js остаются только в визуальном адаптере.
5. Расширить политику активных групп в `validGameObjects`, когда новый генератор/рендер действительно подключены. Актуальный каталог принимает четыре известных здания и одну насосную станцию; ядро проверяет общую уникальность ID.
6. Проверить правила без WebGL, round-trip нового формата, удаление/замену частей, выгрузку ресурсов и отсутствие повторного лута.

Добавление новых типов групп не требует изменения модели/операций ядра. Новый вид компонента требует явного расширения типизированного контракта и его валидатора. Это закрытая схема прототипа, не динамический ECS или универсальный движок.

## Сохранение и восстановление

Активная запись: `desert-walker.survival.v1`, envelope `{ version: 19, state }`; `state.gameObjects.groups` содержит текущие группы и детали. Для единственной фиксированной хижины сохраняется полный снимок экземпляра, а не система дельт бесконечного процедурного мира. Остальные процедурные локации по-прежнему восстанавливаются из генерации, история лута/разборки хранится отдельно. ID деталей строятся из ID группы и ключа prefab, ID соединений также устойчивы.

Версии 1–18 отвергаются без миграций. Удалены старый `hutState.ts` и больше не используемый `inventoryMigration.ts`. Убраны неиспользуемая миграция старой сетки карты и прежняя масса навеса из версии 12; текущая масса и рецепты не менялись. Все существующие проверки актуальных игровых механик сохранены; миграционные ожидания тестов заменены проверками отказа старым версиям в новом наборе.

При несовместимой версии, неизвестном prefab/ресурсе в данных, невалидной группе или повреждённом JSON:

- Показывается предупреждение с экспортом исходного JSON и явной кнопкой новой игры.
- Сцена и игрок не монтируются, применение состояния и запись активного слота блокируются.
- Только нажатие «Начать новую игру с резервной копией» создаёт копию точных исходных байтов под ключом `.backup.<id>`, сохраняет старую запись положения игрока и сбрасывает положение для новой игры.
- Ошибка записи резервной копии блокирует сброс; исходный активный слот не заменяется.
- При обычном сохранении перед записью проверяется полный снимок. Состояние групп живёт в store, а не в компоненте чанка.

Позиция/взгляд продолжают сохраняться отдельной существующей системой `playerSave.ts`. Отсутствующий или не загружающийся файл GLB даёт сообщение/диагностику загрузчика; лут не пересоздаётся и сохранение не сбрасывается. Полноценного экрана восстановления повреждённого файла ассета нет.

## Проверки и ручная приёмка

`npm test` включает `tests/game-objects.mjs`: политики двух тестовых типов без реализации новых механик; ошибочные/занятые сокеты; ID и ссылки; атомарность; добавление/удаление/замена/прочность; world/local transforms в сравнении с Three.js; mapping всех Mesh реального v4; отсутствие новых Mesh/геометрий/материалов; совпадение коллизий с геометрией двери, включая поворот/масштаб группы; открывание через live store; снятие/установка; физический проход; новый экземпляр GLB после выгрузки; перезапуск store; однократный лут, разборка ящика в 4 доски; round-trip; защита несовместимого/повреждённого сохранения и отказ хранилища.

Для ручной проверки запустить `npm run dev`, при старом сохранении экспортировать его и явно начать новую игру. У первой хижины X=12, Z=−15 открыть дверь через E, проверить ящик. Через Escape → «Дебаг» снять дверь; пройти через проём, затем выйти из места установки и установить её. Повторить после открытия двери, ухода на несколько чанков и перезагрузки страницы. В dev-консоли выводятся ID/type/members/connections. Кнопка и лог отсутствуют в production-сборке.

Автоматические проверки не подтверждают графику, FPS, draw calls WebGL или память браузера. Браузер и скриншоты по инструкции пользователя не запускались. Сравнение производительности до/после, фактические рендер-проходы и пользовательское прохождение остаются непроверенными. Дополнительного batching/instancing для v4 не вводилось: сохранены прежние Mesh и общие материалы; соседние варианты продолжают объединяться по материалам.

Проверки завершились успешно: `npm test`, `./node_modules/.bin/tsc --noEmit`, `npm run build`. Команды и конфигурации линтера в проекте нет. Сборка сохраняет предупреждение Vite о чанке больше 500 кБ.

в X=60, Z=−15 у тестовой улицы. Пять деталей: корпус-фундамент, насос,
резервуар, труба и источник питания. После визуального обновления это процедурные модели: цилиндрический бак с обручами и уровнемером, насос с ребристым мотором, генератор с решёткой, труба с фланцами/вентилем и изогнутый кабель.
Рабочей воды, электричества, ремонта, новых рецептов и игровой панели станции нет.

Все детали используют существующие типы, реестры, валидацию и атомарные операции
GameObject core. Четыре `fixed`-связи крепят детали к корпусу; три `port`-связи
задают насос → труба → резервуар и источник питания → насос. Сокеты принимают
только совместимые определения: силовой выход нельзя соединить с водяным входом.
Общий core проверяет занятость сокетов, ID и ссылки. Политика `machine`
проверяет состав, компоненты и монтажные позиции; перед соединением портов
обе детали должны быть закреплены. Перед удалением детали нужно отключить
её порты и крепления. Разъединённые детали остаются участниками группы:
членство и соединения не подменяют друг друга.

Модули находятся в `features/machines/pumpStation`:

- `pumpStationDefinition.ts` — prefab, сокеты, правила и стабильные ID связей.
- `pumpStationWorld.ts` — закреплённая площадка, высота фундамента и начальная группа.
- `pumpStationPhysics.ts` — отдельные AABB деталей из тех же local/world transforms.
- `pumpStationVisual.ts` — подробная геометрия, объединение по материалам и отображение соединений.
- `PumpStation.tsx` — монтирование в пределах двух чанков, управление временем жизни ресурсов.
- `PumpStationDebug.tsx` — dev-лог состава и кнопки соединения трубы/питания.

Геометрии объединяются по материалам внутри каждой детали; материалы общие для станции. Владелец визуального экземпляра освобождает геометрии и материалы через `disposeModelScene` при размонтировании; промежуточная геометрия освобождается после объединения. Изменение связей переключает видимость без пересоздания GPU-ресурсов. Статическая генерация и сборка коллизий не выполняются каждый
кадр; коллизии кешируются существующим `worldObstacles`, ресурсных кешей станции
и дополнительных кадровых подписок нет. Адаптер `streetGroups` теперь выбирает
только здания, чтобы станция не попадала в рендер и взаимодействия домов.

Формат остаётся 19: полный снимок станции хранится в `state.gameObjects`.
Текущие сохранения 19 без площадки получают начальную станцию при загрузке;
имеющийся снимок станции не заменяется генерацией. Отключённые связи, удалённые
детали и состояния компонентов восстанавливаются. Повреждённые данные станции
блокируют запись через существующий экран восстановления. Версии 1–18 по-прежнему
не мигрируются; автоматического сброса нет.

Для ручной проверки: `npm run dev`, подойти к X=60, Z=−15; проверить видимость
деталей, высоту основания и столкновения. Через Escape → «Дебаг» отключить
трубу или питание, перезагрузить страницу и проверить сохранение состояния
кнопок/списка соединений в dev-консоли; затем подключить снова. Уход на несколько
чанков и возврат должен восстановить ту же композицию. При отключении водяного контура труба с вентилем исчезает, её коллизия убирается; при отключении питания исчезает кабель. Насос, резервуар и генератор остаются на месте. При подключении соединительные элементы возвращаются. Частично подключённая труба также скрыта. Логическое членство трубы сохраняется, скрытие не означает удаление детали. Кнопок станции в production нет.

`tests/pump-station.mjs` проверяет реальные machine/building-политики,
несовместимые и занятые порты, атомарный отказ, крепления, удаление деталей,
совпадение AABB с Three.js при повороте/масштабе группы, инвалидирование кеша,
сохранение/перезапуск store и защиту повреждённых сохранений. Этот набор и
`tests/game-objects.mjs` проходят. `npm run build` проходит с прежним предупреждением
о крупном JS-чанке. После актуализации тестов 16 ноября полный `npm test`
проходит: потолок навеса проверяется по полосам двускатной крыши в их собственных
позициях, улица — на настоящем V4 и трёх процедурных домах вместо заменённых GLB.
Проверки коллизий, геометрии, дверей и общих ресурсов сохранены.
Браузер, визуальная проверка и замеры FPS/памяти не выполнялись.


Визуальное обновление станции, 16 ноября: `tests/pump-station.mjs` дополнительно
проверяет реальную подробную геометрию без WebGL: конечность вершин,
вписывание твёрдых деталей в прежние collision envelopes, независимую видимость
трубы/кабеля, восстановление после подключения и создания нового визуального
экземпляра, отсутствие коллизии скрытой трубы и освобождение ресурсов.
Asset ID `pump_station_box:*` сохранены как ключи существующего формата 19;
они теперь разрешаются в подробную геометрию, сброс сохранения не требуется.
Кабель — декоративная связь без отдельного collider. После уточнения 16 ноября он проходит открытой петлёй сбоку от корпусов, имеет оранжевую оболочку и радиус 6,5 см. Геометрическая проверка подтверждает зазор между петлёй и обоими корпусами, а также высоту над фундаментом. Производство воды,
электричество и новые игровые действия по-прежнему не добавлены.
